# Releasing

Releases of the [`njt`](https://www.npmjs.com/package/njt) CLI package follow the changesets flow copied from [kachkaev/repo-dive](https://github.com/kachkaev/repo-dive): merging to `main` never publishes directly.
Instead, the release workflow keeps a "Version packages" PR up to date with pending changesets; merging that PR bumps the version, and the follow-up workflow run publishes to npm.
The Next.js app at the repository root is private and is deployed by Vercel independently of this flow.

## One-time setup (manual steps)

The package already exists on npm, so no initial publish is needed — only the trusted publisher wiring:

1.  **Trusted publisher** — on npmjs.com → package `njt` → Settings → Publishing access, add a GitHub Actions trusted publisher:

    - Organization/user: `kachkaev`
    - Repository: `njt`
    - Workflow: `release.yaml`
    - Environment: `release`

1.  **GitHub environment** — repo Settings → Environments → create `release` (the workflow declares `environment: release`).

1.  **Allow Actions to open PRs** — repo Settings → Actions → General → Workflow permissions → tick "Allow GitHub Actions to create and approve pull requests".
    Without it the changesets action cannot open the "Version packages" PR.
    Note that PRs opened with the default `GITHUB_TOKEN` do not trigger `pull_request` workflows, so the "Version packages" PR shows no CI checks — `release.yaml` re-verifies the CLI build before publishing, but don't make CI checks required for merging that PR.

1.  **Test the pipeline**: once the steps above are done, the next changeset to land should produce a "Version packages" PR whose merge publishes via the trusted publisher, with no npm token anywhere.

## Provenance

`publishConfig.provenance` is set in `cli/package.json`, so CI publishes attach a provenance attestation (the repository is public, which npm requires — provenance statements go to the public Sigstore transparency log and must point at a publicly verifiable source).
Local publishes cannot generate provenance (no CI OIDC identity); if one is ever needed, pass `--provenance=false`.

## Changelog entries

`cli/CHANGELOG.md` is generated by [`@changesets/changelog-github`](https://www.npmjs.com/package/@changesets/changelog-github), configured in `.changeset/config.json`.
Each entry links the pull request that carried the change and the commit it was squashed into.
`disableThanks` is on — this is a solo repository and the attribution would only be noise.

Looking those links up needs the GitHub API, so **`changeset version` requires `GITHUB_TOKEN` in its environment** or it fails outright.
In CI this is taken care of: `changesets/action` passes the token it was given on to the `version` script.
To run `pnpm changesets:version` on a laptop, provide a token yourself:

```sh
GITHUB_TOKEN=... pnpm changesets:version
```

## Day-to-day

- Every user-visible CLI change lands with a changeset (`pnpm changeset`).
- CI (`ci.yaml`) lints and builds the CLI on every push/PR; `release.yaml` re-verifies the build before versioning/publishing.
